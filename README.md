# Supabase 칼럼의 데이터 타입 종류

## 1. Number 종류

- int2 (Samll Integer) : 작은 숫자(-32,768 ~ 32,767)
- int4 (Integer) : 가장 일반적인 숫자(-2,147,483,648 ~ 2,147,483,647)
- int8 (Big Integer) : 아주 큰 숫자(-9조 ~ 9조)
- float4 (Real) : 소숫점이 있는 작은 범위(예: 3.14)
- float8 (Double Precision) : 소숫점이 있는 숫자, 정밀한 값 (예: 3.141519)
- numeric (Decimal) : 엄청 정밀한 소숫점 (예: 1234.141519)

## 2. String 종류

- text : 가장 많이 사용하는 타입, 길이 제한이 없음(예: html 등)
- varchar(숫자) : 길이를 지정함. 남는 공간도 포함(예:이름, 이메일, 주소 등)

## 3. Boolean 종류

- bool : true, false 값만 가질 수 있음. (예: 주문완료, 주문취소 등)

## 4. JSON 종류 (구조화된 즉 `{키명:값, 키명:값...}`)

- json : 글자입니다. (예: `{이름:아이유, 나이:18, ...}` )
- jsonb : 더 빠르게 검색이 가능한 형태의 바이너리 코드로 변환한 자료형.
- 참고사항으로 Firebase, Mongo DB 에서 이타입을 사용함.

## 5. 독특한 데이터 타입

- uuid : 고유한 ID 를 저장할 때 (`pk` 로 추천)
- bytea : 파일, 이미지 등을 저장할 수 있다. (사용은 고민필요)

## 6. Date & Time (날짜와 시간 데이터)

- date : 연, 월, 일 (예: 2025-09-19)
- time : 시간만 저장 (예: 19:09:50)
- timetz: 시간 + 시간대 (예: 19:09:50+09)
- timestamp: 날짜 + 시간 (예: 2025-09-19 19:09:50)
- `timestamptz`: 날짜 + 시간 + 시간대 (예: 2025-09-19 19:09:50+09)

### 6.1. 왜 timestamptz 를 권장하는가?

- 세계 어느 나라에 가도 정확한 시간 유지
- 시간대가 바뀌어도 문제 없음.
- FE 에서 별도로 변환안해도 됨.

### 6.2. 회원 정보 테이블(profiles 예제)

```sql
create table profiles (
  id uuid primary key default gen_random_uuid(),
  email text unique not null,
  role text check (role in ('admin', 'operator', 'member', 'guest')) default 'member',
  create_at timestamptz default now(),
  updated_at timestamptz default now()
);

```

### 6.3. 메모 테이블(memos 예제)

```sql
create table memos (
  id uuid primary key default gen_random_uuid(),
  user_id uuid reference profiles(id) on delete cascade,
  content text not null,
  tags text[],
  metadata jsonb, -- 추가 정보( {"likes": 10, "shard": true} )
  created_at timestamptz default now()
);

```

# Supabase RLS (Row Level Security)의 이해

- `행 단위로 접근을 제한한다.`
- 다른 DBMS 는 RLS 가 없습니다. (DB관리자가 별도로 작업)
- 데이터를 관리할 때 자격을 제한한다.
- RLS 를 설정하지 않으면 CRUD 가 자유롭다.
- 처음에는 RLS 에 대해서 적용을 하지 않고 개발을 시작한다.
- 하지만, 결국 RLS 가 필요하므로 미리 셋팅에 대해서 고민을 하여야 한다.

## 1. RLS 정의 단계

### 1 단계 : `테이블을 먼저 정의 및 생성` 한다.

### 2 단계 : RLS 를 활성화 시킨다.

```sql
alter table memos enable row level security;

```

### 3 단계 : 정책(policy) 를 만든다.

- select, insert, update, delete 별도로 각각 정의 한다.

## 2. Policy 생성법 (create policy 사용법)

### 2.1. 기본 구조

- `이름문자열`은 중복해서 여러 번 생성 불가

```sql
create policy "이름문자열"
on 테이블명
for [select | insert | update | delete | all]
using (auth.uid() = owner)

```

### 2.2. 다양한 예제

- 나의 memo 만 보기

```sql
create policy "Users can view ther own rows Memo"
on memos
for select
using (auth.uid() = user_id);

```

- 나의 memo 만 수정하기

```sql
create policy "Users can update 나만 Memo"
on memos
for update
using (auth.uid() = user_id);

```

- 모두가 볼 수 는 있다. 하지만 수정은 작성자만 가능하다.

```sql
create policy "Anyone can view Memo"
on memos
for select
using (true);

create policy "Onlycan owner can update Memo"
on memos
for update
using (auth.uid() = user_id);

```

- 특정 조건 만족 시 접근 가능

```sql
create policy "Anyone can view public Memo"
on memos
for select
using (is_public = true OR auth.uid() = user_id );

```

- 시간 지정해서 접근 가능하게

```sql
create policy "Update before Memo"
on memos
for update
using (auth.uid() = user_id AND now() < deadline);

```

## 3. Policy 해제하기

```sql
alter table 테이블명 disable row level security

```

```sql
alter table memos disable row level security

```

## 4. 현재 Policy 상태 확인하기

- policy 도 별도의 테이블에 관리되고 있다.

```sql
select relrowsecurity, relforcerowsecurity
from pg_class
where relname = 'momos';

```

# Supabase RLS 예제

## 1. 시나리오

- 관리자, 부운영자, 회원, 비회원이 있다.
- memos 테이블이 있다.
- 회원의 등급에 따라서 memos 접근을 제어하려고 한다.
- `memos 테이블 sql`

```sql
create table memos (
  id bigint generated by default as identity primary key,
  user_id uuid references auth.users not null,
  content text not null,
  is_public boolean default false,
  created_at timestamp default now()
);

```

- `profiles 테이블 sql`

```sql
create table profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  email text unique,
  role text check (role in ('admin', 'manager', 'member', 'guest')) default 'member',
  created_at timestamp default now()
);

```

## 2. profiles 테이블이 있다는 가정하에 진행

- role 칼럼이 없을 경우라면

```sql
alter table profiles add column 칼럼명 데이터종류
제한값 ( 칼럼명 in ("값1", "값2", "값3", "값4") )
default "값"

```

```sql
alter table profiles add column role text
check ( role in ("admin", "manager", "member", "guest") )
default "guest"

```

## 3. 역할(Role) 정의

- admin : 관리자
- manager : 부관리자
- member : 회원
- guest : 비회원

## 4. memos 테이블에 권한 주기

### 4.1. admin 은 모든 접근 가능

```sql
create policy "Admim full access"
on memos
for all
using ( exist (
  select 1 from profiles
  where id = auth.uid() AND role ="admin"
) )

```

### 4.2. manager 은 읽기/수정만 가능

```sql
create policy "Manager Read and Update"
on memos
for select, update
using ( exist (
  select 1 from profiles
  where id = auth.uid() AND role ="manager"
) )

```

### 4.3. member 은 본인 글만 접근 가능

```sql
create policy "Member can access their own Memos"
on memos
for all
using ( auth.uid() = user_id AND exist (
  select 1 from profiles
  where id = auth.uid() AND role ="member"
) )

```

### 4.4. guest 는 공개된 글만 조회 가능

```sql
create policy "Guests can only read public memos"
on memos
for select
using ( is_public = true);

```
